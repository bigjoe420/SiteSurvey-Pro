The back-button multi-tap saga — RESOLVED 2026-08-31 (read this first)
=====================================================================
Symptom: back button needed multiple taps 30–50% on Wi-Fi/BLE; other screens fine.
Root-cause chain, in order of discovery:
1. Sampler hardening (prio 24 + vTaskDelayUntil) — correct on its own merits,
   kept permanently, but NOT the cause of the misses.
2. Temporary DIAG instrumentation (touch DOWN/UP logging + PRESSED/RELEASED/
   CLICKED callbacks on all four back buttons) EXONERATED the firmware:
   70/70 in-zone PRESSED → CLICKED, zero sample loss, zero event-semantics
   failures. Every genuine miss landed BELOW the hit zone.
3. Geometry fix in two steps: ext 8→24 killed the y45–59 dead strip (~97.5%
   first-tap); residual corner cluster x84–88/y62–68 (habitual thumb landing,
   2–8 px below zone bottom) killed by ext 24→32. Zone y≤68/x≤116; back button
   topmost so it wins the overlap with list row 1's top 4 px.
4. FREEZE INCIDENT (08-31): "tap tap tap, nothing, then it works" — caused by
   per-tap diag logs + CONFIG_ESP_CONSOLE_SECONDARY_USB_SERIAL_JTAG=y + no
   monitor draining COM7: the secondary console BLOCKS the calling task when
   unread, stalling ui_task. Diag fully stripped; freezes gone (owner-verified).
   LESSON: never leave per-event logging enabled on this console config without
   a monitor attached. One-line hardening candidate: disable
   CONFIG_ESP_CONSOLE_SECONDARY_USB_SERIAL_JTAG (not applied — owner's call).
